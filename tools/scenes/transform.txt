# The transform story. A transform is a *task in flight*, not a tool: it exists only between Begin
# and Apply, and it has a Cancel. So it has no panel of its own on show -- it borrows Tool options
# while it is in the air and gives it back the moment it ends, which is what
# `docs/CONTEXTUAL_PANELS.md` means by transient. A scene that never lifts anything never sees any
# of its controls at all, which is the point: the panel is the brush's until there is a transform.
#
# **Beginning one is a command, and commands live in menus and on the keyboard.** Ctrl+T here, and
# Edit > Transform selection, which `menu.txt` drives. It used to be a button in a Transform panel
# that had to be permanently on show for the sake of a task lasting a few seconds.
#
# The standalone Transform panel still exists -- every section does, for anyone who wants it docked
# somewhere permanently -- and the last block of this scene opens it from the panel list to drive
# the two shapes that cannot be reached any other way: the filter with nothing in the air, and what
# the panel says when there is nothing to lift.
#
# **Where the canvas points come from.** In a 2200x1450 window the canvas viewport is about
# x 330..1450 by y 130..1250 -- a square of roughly 1120 -- and `View::fit` takes the smaller of
# viewport/page and keeps 6% as margin, so a 2048-square page rests at about 1120/2048 * 0.94 =
# 0.51, which is asserted below rather than assumed. At that scale the page covers 890+-526 by
# 690+-526, that is x 364..1416 by y 164..1216. Everything here happens inside 660..1120 by
# 460..920, well within the page and clear of the rail and the panel column.
#
# **And the handle box is that rectangle.** `begin_transform` builds the box from the selection
# mask's `content_bounds`, so a rectangle dragged from (660,460) to (1120,920) puts its corner
# handles at exactly those screen points, to within the pixel the page round-trip costs. That is
# how the corner drag below knows where to grab, and `GRAB_PX` gives it ten screen pixels of slack.
#
# **What each control is answerable to.** `report_state` now describes a transform while it is in
# the air -- `transform.scale`, `transform.rotation`, `transform.offset`, `transform.lock`,
# `transform.kernel`, `transform.persistent` -- and reports the application's own filter, `kernel`,
# whether or not anything is in flight. Before that, seven controls shared the one assertion
# `status Applied the transform`, which says only that the transform was not the identity: true of
# any control that did anything at all, and just as true with Scale X wired to Scale Y. Each block
# below checks the number its own control is supposed to move, and checks that the numbers beside
# it did not move.
#
# **How a scale is asserted, and why it is asserted as a pair.** `transform.scale` is two numbers
# on one line, and `about` reads one number, so it cannot serve here at all -- `expect`, and an
# exact pair, is the only assertion available. A slider dragged to the middle of its track lands
# near its target and not on it, which is no use to an exact assertion, so each scale block drives
# its slider *past* the end of the track instead: `from_fraction` is the one place a slider's range
# is enforced, `panel_draw` keeps a latched slider following the pointer wherever it has got to,
# and together those pin the value at exactly `SCALE_MIN` -- 10%, a scale of 0.1000. The axis under
# test then reads 0.1000 and the axis beside it has to still read 1.0000, so swapping the two ids
# fails both blocks. The fraction is negative because the low end of the track is to the left, over
# the canvas; a drag off the right-hand end of the panel would be a drag off the screen.
expect tool Brush
expect select-tool -
expect selection false
expect dragging false
expect undo 0
expect redo 0
expect dirty false
expect page-size 2048	2048
# Measured, not derived: the application reports 0.5916 for a 2048 page in this window.
about zoom 0.5916 0.02
# The filter the next transform will use, before anybody has touched it: `Kernel::default`.
expect kernel Mitchell

# A transform that has just been lifted is the identity, hung on the filter that was chosen with
# nothing in flight, and it is *persistent*: it stays up until Apply, Cancel, Enter or Esc ends it.
# The `false` a quick move-drag reports cannot be seen from here at all -- it exists only between a
# press and a release, and the harness reads the state between steps.

# From here every block is the same shape: begin, move one control, apply, undo. Undoing an
# `Op::Move` brings the outline back with the pixels, so each block starts from the same document
# and the same handle box as the last -- which is what lets one set of coordinates serve them all.
# `status Applied the transform` stays in every block, because `commit_transform` says it only when
# the transform is not the identity and that is still worth knowing; it is no longer the only thing
# a block proves.

# And what it does to a *corner*, which is the gesture the lock exists for and a different piece of
# code from the sliders: `transform_box::scale` projects the drag onto the diagonal instead of
# reading the two axes off it separately. Two numbers that came off a pointer cannot be asserted --
# `expect` wants them exact and `about` cannot read a two-number line -- so what is asserted here is
# what the pixels do, which is the difference the lock makes and has nothing to do with the panel.
#
# **And it can now say "those two numbers are equal"**, which is what the projection actually
# promises: `transform.scale-x` and `transform.scale-y` are reported on their own as well as
# together, so each can be checked to a tolerance and a lock that moved only one axis fails. The
# pixel check below stays, because it is a statement about the artwork rather than about the panel,
# and the two together say the lock reaches both.
#
# The bottom-right handle is at (1120,920) and it is dragged straight down to (1120,1180). Unlocked
# that stretches the height alone: the content still ends at x 1120, so the box out to its right
# stays as clean as it was before the drag. Locked, the same drag takes the width with it --
# k = (460 + 720) / (2 * 460) = 1.283, so the content reaches x 660 + 460*1.283 = 1250 and the far
# end of the stroke lands at (1199,999), crossing the box that was empty a moment ago. Apply's
# status is in both halves because an `ink ... 0` alone would also pass if the grab had missed.
key ctrl+t
expect transform.lock false
ink 1135 900 1235 1010 0
drag 1120 920 1120 1180
expect dragging true
# Unlocked, the drag is all height: x stays where it was and y grows by the ratio above.
about transform.scale-x 1.0 0.02
about transform.scale-y 1.57 0.2
ink 1135 900 1235 1010 0
shot transform-corner-unlocked
press Tool options:Apply
expect status Applied the transform
expect undo 2
key ctrl+z
expect undo 1
expect selection true

key ctrl+t
press Tool options:Lock
expect transform.lock true
drag 1120 920 1120 1180
expect dragging true
expect transform.lock true
# Locked, the projection puts the same number on both axes -- which is the promise, and which
# nothing could say until each axis was reported on its own.
about transform.scale-x 1.28 0.15
about transform.scale-y 1.28 0.15
ink 1135 900 1235 1010 20
shot transform-corner-locked
press Tool options:Apply
expect status Applied the transform
expect undo 2
key ctrl+z
expect undo 1
expect selection true
expect status Moved the selection back

# The canvas is the instrument, and the interior of the box is the plainest gesture on it: a press
# inside grabs the interior and the floating pixels follow the pointer. `Handle::Inside` rounds the
# total to whole page pixels so a move still takes the lossless copy path, and 100 screen pixels at
# the 0.5916 this window reports is 169.03 page pixels, which rounds to 169. That is the number to
# re-derive if the window size or the fit ever changes; nothing else here leans on the zoom to more

# Just outside the box is the rotation ring, the third thing a press on the canvas can mean. It
# reaches `ROTATE_BAND` times the ten screen pixels of `GRAB_PX`, so twenty pixels clear of the
# right-hand edge is inside the ring and clear of the edge handle, which wants ten. The box turns
# about its own centre, which is (890,690): the press is due right of it at zero degrees and the
# release is down and to the right at forty-five, so the transform turns by 0.7854 radians. Off a
# pointer, so `about` -- and rotation is one number, which is what lets `about` serve at all.

# --- The section is still a panel, and that is where the other two shapes live ---
#
# Sections rather than tabs is the answer to "some people want it always in one place": the same
# module serves the contextual panel and a standalone one, opened from the panel list and docked
# wherever the artist likes. Opened here because it is the only way to see what the transform
# section says when nothing is in the air -- Tool options is the brush's then, correctly.
#
# The list is reached with a secondary press anywhere, which is the workspace's own gesture, and
# switching a panel *on* puts it in the air rather than anywhere in particular -- the click after it
# is what says where. Without that click the panel is in neither tree, and the three `absent`s below
# pass for the wrong reason: `docs/DRIVING.md` warns about exactly that, and this scene was written
# without the click and demonstrated it before the run stopped a step later.
