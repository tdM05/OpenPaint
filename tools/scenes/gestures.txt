# Every panel gesture the workspace offers, and what each one does to the arrangement.
#
# **Run this at 2200 by 1450.** Every coordinate below was read off `target/drive/layers.controls`,
# which is a 2200x1450 run: the client area is 2178 by 1394 physical pixels at 1.5 pixels per
# point, so a 28-point header is 42 pixels and a 22-point row is 33. Slot rectangles come from the
# `$` lines of that atlas plus the 8-point padding a panel insets its contents by. At any other
# size the numbers are wrong and the run will stop on a press that lands nowhere, which is the
# right way for it to fail.
#
# **No tab is named by where it happens to be.** Tabs are laid out from measured labels, so any
# label changing moves the rest -- and this scene's arrangement changed wholesale when Brush,
# Select, Transform and Text stopped being four tabs of one slot. Every tab here is reached with
# `tab`, `holdtab` or `dragtab`, which read the atlas; only slot *centres* are written as numbers,
# and the three bands of the right-hand column keep the weights they always had.
#
# **The arrangement is the only witness.** A panel moved, floated, docked or closed changes no
# document state and a screenshot cannot be asserted on, so every gesture here is proved through
# the `layout` key -- slots in the order they resolve, each a comma-separated list of its tabs with
# the one on show marked `*`, then ` | ` and the floating windows.
#
# **Why a window is floated before anything else is asserted.** `Workspace::describe` writes
# `"{slots} | {windows}"`, so an arrangement with no floating windows ends in a space, and the
# harness trims both the scene line and the value it compares -- which makes an `expect layout` for
# a floating-free arrangement impossible to satisfy. Everything below therefore keeps at least one
# window out, and the two states this scene cannot assert (the arrangement it starts from and the
# one it restores) are marked where they occur. Trimming `$got` in `Expect-State`, or dropping the
# trailing space from `describe`, would close that gap.
#
# **`hold` does not arm a drag, and `drag` does not need it to.** `docs/DRIVING.md` says nothing
# rearranges the workspace until the pointer has been held for `panel_drag::HOLD_MS`; the code says
# the opposite and has since "Grab at once, hold to ask". `Grab::moved` gates only whether anything
# *has* moved, a tab is taken the instant it is pressed, and holding one still for 320 ms drops the
# grab and asks the panel for its settings instead. So a panel is moved with `drag`, and `hold` on
# a tab is what opens a settings popup -- which is asserted below rather than assumed. `hold` is
# still the right step for a window's edge, which asks nothing on a hold and goes on resizing.

# --- What we start from, and a stroke to prove the layout stack never touches the artwork ---
#
# The arrangement here is the built-in one and cannot be written as an `expect layout` for the
# reason in the header; it is `*Menu / *Tools / *Canvas / *Layers,Properties,History,Pages,Page /
# *Tool options / *Colour` with nothing floating. Two of those are contextual panels -- Tool
# options follows the tool in hand and Properties follows the active layer -- and nothing in this
# scene depends on that: to the workspace they are ordinary panels in the layout tree, which is the
# whole claim `docs/CONTEXTUAL_PANELS.md` makes about them, and this file is where it is tested.
expect undo 0
expect redo 0
expect dirty false
ink 600 400 800 600 0
drag 500 300 900 700
expect undo 1
expect dirty true
ink 600 400 800 600 20
shot gestures-start

# --- Holding a tab asks that panel what it offers, and Float lifts it out of the arrangement ---
#
# The Page tab is the last one in the Layers group, so taking it out leaves every other tab and
# every slot exactly where the atlas says it is -- which is what the rest of this scene relies on.
# Pressing Float proves the popup was really open: a name the application is not drawing stops the
# run rather than clicking nowhere.
holdtab Page

# of `drag`. The arrangement is unchanged, and Properties' settings are open -- which the Remove

# switching it off in the panel list, and it is undoable like any other change to the arrangement.

# --- Dragging a tab into another slot moves the panel ---
#
# The History tab, from the Layers group into the middle of the Tool options slot. The middle of a
# leaf is its centre zone, so History arrives as another tab there and is the one shown; the group
# it left keeps Layers in front. The drop point is the centre of the Tool options slot, the middle
# band of the right-hand column.
dragtabto History 1970 820
expect layout *Menu / *Tools / *Canvas / *Layers,Properties / Tool options,*History / *Colour | Page / Pages
shot gestures-moved

# --- Layout undo, redo and the tab tap that leaves no trace ---
#
# Switching tab between the move and the undo is the point of this block: if a tap were recorded,
# the first F3 would take back the tab switch and stop there. It goes straight back past it to the
# arrangement as it stood before the drag, tab selection and all, which is one entry for one
# gesture and none for a tap. The artwork's own stack is untouched throughout.
tab Tool options
expect layout *Menu / *Tools / *Canvas / *Layers,Properties / *Tool options,History / *Colour | Page / Pages
key f3
expect layout *Menu / *Tools / *Canvas / *Layers,Properties,History / *Tool options / *Colour | Page / Pages
expect undo 1
expect redo 0
expect dirty true
# Redo puts back the arrangement as it stood at the moment of the undo, and at that moment the tab
# tap above had already changed which one was showing. So History comes back to the Tool options
# slot with Tool options still in front -- not because the tap was recorded, but because it was
# never undone. The two claims sit together consistently: undo walks arrangements and skips taps;
# redo restores what you actually had.
key shift+f3
expect layout *Menu / *Tools / *Canvas / *Layers,Properties / *Tool options,History / *Colour | Page / Pages
expect undo 1
expect redo 0

# --- Resizing a floating window by its edge and by its corner ---
#
# **A window's size is now something the application will say**, so a resize is asserted as a
# resize rather than only as a step on the layout stack -- which is true of any change and silent
# about the size. `windows` gives each floating window as `x,y wxh` in points, in the order they
# were lifted. The undo-step reasoning below is kept as well: between them they say that the drag
# changed the size, and that it recorded exactly one change and not two.
#
# The Pages window is the second one lifted, and a second window lands *beside* the first rather
# than cascading over it -- 387,60 by 319x325 points, which is 580,90 by 479x488 pixels. Its right
# edge is therefore at x 1059 and its bottom at y 578. The grab band straddles each edge by half of
# the 26-point splitter reach, so 1066,334 is on the right edge and 1066,584 is the bottom-right
# corner. `hold` is right here where it is wrong on a tab: an edge is grabbed the instant it is
# touched and asks nothing when it is held still.
#
# **These numbers were 88,88 until the placement changed under them.** The scene went on running,
# pressing empty canvas where it meant a window's edge, and what came out looked like windows
# vanishing on their own. A coordinate that names nothing is the most expensive kind of stale.
#
# The arrangement is still the one the move above left, so a resize that recorded nothing would
# send the F3 after it back past the move instead; a resize that recorded two would need two. One
# F3, and the arrangement is unchanged: exactly one step, and it also puts the window back to the
# size and place it started at, which is what makes the corner grab below land where it is aimed.
# The presses that begin on the border lie over the canvas, and the artwork's undo depth says
# neither of them painted.
shot gestures-window-before
expect windows 60,60 319x325 / 387,60 319x325
hold 1066 334 1246 334
# 180 screen pixels wider is 120 points wider, and only the width moves.
expect windows 60,60 319x325 / 387,60 439x325
shot gestures-window-wider
key f3
expect windows 60,60 319x325 / 387,60 319x325
expect layout *Menu / *Tools / *Canvas / *Layers,Properties / *Tool options,History / *Colour | Page / Pages
expect undo 1
hold 1066 584 1216 704
# A corner takes both: 150 screen pixels across and 120 down, which is 100 and 80 in points.
expect windows 60,60 319x325 / 387,60 419x405
shot gestures-window-corner
key f3
expect windows 60,60 319x325 / 387,60 319x325
expect layout *Menu / *Tools / *Canvas / *Layers,Properties / *Tool options,History / *Colour | Page / Pages
expect undo 1
expect dirty true
key f3
expect layout *Menu / *Tools / *Canvas / *Layers,Properties,History / *Tool options / *Colour | Page / Pages

# --- A docked tab dragged out over the canvas stays docked ---
#
# `docs/PANEL_GESTURES.md` is explicit that dragging never crosses between docked and floating, and
# this is what that means in practice: the Colour tab let go in the middle of the canvas becomes a
# tab of the *canvas* slot rather than a window, and because Colour was the only tab in its slot,
# that slot goes away and the right-hand column collapses from three to two. Colour is the panel on
# show there, so the artwork is behind it -- which is why there is no ink assertion here.
#
# The pointer crosses the whole canvas with the button down and the undo depth does not move, which
# is the assertion that a panel gesture owns the pointer and no stroke was painted under it.
dragtabto Colour 958 720
expect layout *Menu / *Tools / Canvas,*Colour / *Layers,Properties,History / *Tool options | Page / Pages
expect undo 1
shot gestures-onto-canvas
key f3
expect layout *Menu / *Tools / *Canvas / *Layers,Properties,History / *Tool options / *Colour | Page / Pages

# --- A floating window dragged over a slot stays floating ---
#
# The other half of the same rule. The Page window is taken by its tab and let go in the middle of
# the Layers slot, which is where the block above dropped a docked panel and where the pick below
# will drop this one. It lands nowhere: the window has been carried and that is all, and the
# arrangement is untouched. The carry is still one entry on the layout stack, and taking it back is
# also what puts the window back where the hold that follows expects it.
#
# **The windows swap places in the line and that is not a change to the arrangement.** `describe`
# lists them back to front, so taking Page by its tab brings it forward and it is written last --
# and the F3 after it does not put the order back, because which window is in front follows the
# pointer and is not something the layout stack records. Same rule as a tab tap leaving no trace.
dragtab Page 1799 179
expect layout *Menu / *Tools / *Canvas / *Layers,Properties,History / *Tool options / *Colour | Pages / Page
shot gestures-window-carried
key f3
expect layout *Menu / *Tools / *Canvas / *Layers,Properties,History / *Tool options / *Colour | Pages / Page

# --- Put back into: the way across from floating to docked ---
#
# Holding the window's tab asks the panel it is showing, and a floating panel is offered "Put back
# into..." where a docked one is offered "Float". It names no destination: the window stops
# floating and the next press says where it goes, so the click on the middle of the Layers slot is
# the answer to a question rather than a drop. Page arrives as a tab there and is the one shown.
#
# The state between the two -- Page in neither tree while the pick waits -- has no floating window
# and so cannot be written as an `expect layout`.
holdtab Page
shot gestures-window-settings
press Put back into...
click 1970 335
expect layout *Menu / *Tools / *Canvas / Layers,Properties,History,*Page / *Tool options / *Colour | Pages
shot gestures-docked-again

# --- The panel list, from a secondary press on the workspace's own ground ---
#
# The canvas draws no contents of its own, so the other button there means the workspace rather
# than the panel: this is the route that survives an arrangement with everything closed. Switching
# History off takes it out and leaves the list up, so putting it back is the next press in the same
# list; switching it on starts the same pick that "Put back into..." does, and the click says

# --- Controls run ---
#
# Which way a panel's controls run is not part of the arrangement, so it has a key of its own
# (`directions`, one entry per panel). It used to have neither, and the pictures either side were
# the whole of the evidence that the panel had turned at all.
#
# The Menu is asked with the other button rather than by holding it. A compact panel is all panel
# strip, and `window_target` turns a docked strip into `Elsewhere`, so holding one asks nothing at
# all -- which the table in `docs/PANEL_GESTURES.md` says should give that panel's settings. The
# secondary press does reach it, through `header_under`, which is what this uses. Across and
# Whichever fits both put a wide panel's handle down its left-hand side, so the bar stays where it
# is and the settings stay reachable at the same point.
right 14 30
shot gestures-menu-settings
press Menu:Across
expect directions Menu=across Tools=wrapped Canvas=down Brush=down Layers=down Colour=down History=down Transform=down Pages=down Page=down Text=down Select=down Tool options=down Properties=down
expect layout *Menu / *Tools / *Canvas / Layers,Properties,History,*Page / *Tool options / *Colour | Pages
shot gestures-menu-across
right 14 30
press Menu:Whichever fits
expect directions Menu=fits Tools=wrapped Canvas=down Brush=down Layers=down Colour=down History=down Transform=down Pages=down Page=down Text=down Select=down Tool options=down Properties=down
expect layout *Menu / *Tools / *Canvas / Layers,Properties,History,*Page / *Tool options / *Colour | Pages
key escape

# --- Layout reset, and the one thing it does not reset ---
#
# Ctrl+F3 puts the arrangement back to the built-in one, which is asserted here in full: every slot
# and every tab in the order the workspace resolves them, and no floating windows -- the built-in
# arrangement has none, and a panel left out in the air while its default slot was restored was in
# the workspace twice. "Everything back where it started" cannot leave half of it where it was.
#
# The reset goes on the layout stack like every other change, so F3 takes it back whole.
key ctrl+f3
expect layout *Menu / *Tools / *Canvas / *Layers,Properties,History,Pages,Page / *Tool options / *Colour
shot gestures-reset
key f3
expect layout *Menu / *Tools / *Canvas / Layers,Properties,History,*Page / *Tool options / *Colour | Pages
expect undo 1
expect redo 0
